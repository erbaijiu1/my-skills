# Multi-Project Path Prefixing

当多个克隆站点需要部署在同一台服务器、同一个网关或同一个域名下的不同子路径时，可以采用业务隔离前缀方案，例如 siteCode。

这不是默认必选项。只有在目标仓库已经采用此模式，或部署环境明确要求子路径隔离时，才引入它。

## 适用场景

- 多个站点共享同一个域名，需要按子路径区分。
- 前台、后台和 API 需要避免路径冲突。
- 反向代理、Nginx 或网关层已经存在统一前缀规则。

## 建议做法

### Frontend Nuxt

- 如果前台页面挂载在子路径下，可将 app.baseURL 设为 /{siteCode}/。
- 前端请求 API 时，优先复用仓库现有的 config 或 runtimeConfig 约定，不要在组件里散落拼接前缀。
- 如果运行在容器中并需要被外部代理访问，检查监听地址是否允许外部访问，例如绑定到 0.0.0.0。

### Admin Dashboard

- 如果后台系统也部署在同域子路径下，可为其分配独立前缀，例如 /{siteCode}_admin/。
- 管理端的 base、router history 和 API baseURL 应保持一致，避免前后台混淆。

### Backend FastAPI

- 若已有多站点路由约定，可在 API 层统一挂载 /{siteCode}/api/...。
- 如果现有后端并未使用该模式，不要只为了“统一”而强制加这一层。

## 检查点

- 页面路由、静态资源路径和 API 路径是否都遵循同一前缀规则。
- Nginx、Ingress、Traefik 或其他网关配置是否同步更新。
- 文档、环境变量和前端配置是否统一引用该前缀。
